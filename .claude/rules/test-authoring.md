# Test authoring

- **Scope = the title.** One behaviour per test, stated in its title. No extra assertions; add a step only when the title's flow can't be reached or verified without it.
- **Tags:** every test carries its feature (`@FEAT-…`, usually on the `describe`) and each business rule it proves (`@BR-…`). `@smoke` marks the critical path, `@journey` multi-step API journeys, and `@readonly` a test that changes nothing (no `seed`, no `customer`, no writes). Only `@readonly` tests run on live. Traceability and impact selection read these tags.
- **Setup is not the test.** Data comes from the `arrange` fixture (a named recipe from `framework/setup/recipes.ts`, which is the start state a manual case arranges with `bun run qa:arrange --case`), `seed.*` (`customer`, `product({ priceCents, stock })`, `coupon`, `cart`, `order`, `shipped`, `cancelled`, `lockedOut`) or fixtures. Never use UI clicks unless the UI flow is the title. A test creates the data it changes; seeded catalog data is read-only (see `LRN-TEST-DATA`).
- **Who the test acts as:** `test.use({ account: Account.… })` signs the browser in from a storage state, never through the login form. Use `NEW_CUSTOMER` (the `customer` fixture, fresh per test) for anything that changes per-user state. `RETURNING_CUSTOMER` (saved, with order history; the `user` fixture) is only for read-only checks, because every test on every environment shares it. `GUEST` is the default. In API specs, use `api.as(customer)` / `api.as(user)`.
- **API specs:** call helpers (`api.as(customer).cart.add(...)`), assert refusals with `expectRefused(call, status, code)`, send malformed bodies with `api.raw(...)`. Endpoint specs live in `tests/api/endpoints/<resource>.spec.ts`, one `describe` per endpoint, positive then negative cases, boundaries from the rule document.
- **Journey specs** (`tests/api/journeys/`) chain the calls of one business flow entirely over the API, every phase in a `test.step` named as the business action (`'Bob is refused at checkout'`). They end on the business outcome (state, stock, history) rather than on a status code.
- **UI specs:** only through page objects (`framework/pages/`); no raw locators in specs. Page-object actions that call the API wait for that response (`waitForResponse` set up before the click); navigation waits on `body[data-ready]`. Role/label locators; `exact: true` when one label contains another.
- **Steps:** a test reads as Given / When / Then `test.step`s named in business words (`'Given a $40.00 cart'`, `'When WELCOME10 is applied'`, `'Then 10 % is taken off the subtotal'`); a refusal is one step that names it (`'Adding 11 units is refused: 422 QTY_LIMIT'`). Every assertion (`expect` and `expectRefused`) sits inside a step (ESLint enforces it). Page-object and seed methods also carry `@step('…')` (`@step((id: string) => \`Open order ${id}\`)` for arguments) and API calls report themselves as `METHOD /path`, so the report reads as business actions.
- **Assertions** use web-first `expect(locator)` in UI tests, with exact values (cents, messages) from the rule documents. Every `expect` carries a message that says what it checks and why the value is right (ESLint enforces the message): `expect(orderPage.cancelButton, '"Cancel order" is not offered for a shipped order').toBeHidden()`, `expect(cart.discountCents, '15% of $300.00 capped at $30.00').toBe(3000)`. Never use a bare noun like `'subtotal'`. Compare arrays directly rather than with `every(...)).toBe(true)` so a failure shows the difference.
- **Imports** through tsconfig path aliases only (`@api`, `@pages/*`, `@utils/*`, …), never `./` or `../`. Dates through `@utils/date` (date-fns), never `Date` or date-fns directly. ESLint enforces both.
- **Known product bug:** `test.fail(true, 'DEF-xxx: …')` placed after setup, title starting with the defect id, plus `@DEF-xxx`.
- **Validate:** run the new or changed tests with `--grep`, then `bun run typecheck` and `bun run lint`; run a `@readonly` test with `TEST_ENV=live` too. If a failure can't be explained from the code, go look at the app (browser or API) instead of loosening the test.
