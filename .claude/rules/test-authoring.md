# Test authoring

- **Scope = the title.** One behaviour per test, stated in its title. No extra assertions; add a step only when the title's flow can't be reached or verified without it.
- **Tags:** every test carries its feature (`@FEAT-…`, usually on the `describe`) and each business rule it proves (`@BR-…`). `@smoke` marks the critical path, `@journey` multi-step API journeys, `@readonly` a test that changes nothing (no `seed`, no `customer`, no writes) — the only tests that run on live. Traceability and impact selection read these.
- **Setup is not the test.** Data comes from `seed.*` (`customer`, `product({ priceCents, stock })`, `coupon`, `cart`, `order`, `shipped`) or fixtures — never UI clicks, unless the UI flow is the title. A test creates the data it changes; seeded catalog data is read-only (see `LRN-TEST-DATA`).
- **Who the test acts as:** `test.use({ account: Account.… })` signs the browser in from a storage state, never through the login form. `NEW_CUSTOMER` (the `customer` fixture, fresh per test) for anything that changes per-user state; `RETURNING_CUSTOMER` (saved, with order history; the `user` fixture) only for read-only checks — it is shared by every test, on every environment; `GUEST` is the default. In API specs `api.as(customer)` / `api.as(user)`.
- **API specs:** call helpers (`api.as(customer).cart.add(...)`), assert refusals with `expectRefused(call, status, code)`, send malformed bodies with `api.raw(...)`. Endpoint specs live in `tests/api/endpoints/<resource>.spec.ts`, one `describe` per endpoint, positive then negative cases, boundaries from the rule document.
- **Journey specs** (`tests/api/journeys/`) chain the calls of one business flow entirely over the API, every phase in a `test.step` named as the business action (`'Bob is refused at checkout'`), and end on the business outcome (state, stock, history), not on a status code.
- **UI specs:** only through page objects (`framework/pages/`); no raw locators in specs. Page-object actions that call the API wait for that response (`waitForResponse` set up before the click); navigation waits on `body[data-ready]`. Role/label locators; `exact: true` when one label contains another.
- **Steps:** every page-object and seed method carries `@step('…')` (`@step((id: string) => \`Open order ${id}\`)` for arguments) and API calls report themselves as `METHOD /path`, so the report reads as business actions. An action done inline in a spec goes in a `test.step`.
- **Assertions** use web-first `expect(locator)` in UI tests; exact values (cents, messages) from the rule documents. Every `expect` whose subject and matcher don't say what is being checked carries a message — always for visible/hidden/enabled/count, status codes, stock, lengths and booleans: `expect(orderPage.cancelButton, '"Cancel order" is not offered for a shipped order').toBeHidden()`. Compare arrays over `every(...)).toBe(true)` so a failure shows the difference.
- **Imports** through tsconfig path aliases only (`@api`, `@pages/*`, `@utils/*`, …), never `./` or `../`. Dates through `@utils/date` (date-fns), never `Date` or date-fns directly. ESLint enforces both.
- **Known product bug:** `test.fail(true, 'DEF-xxx: …')` placed after setup, title starting with the defect id, plus `@DEF-xxx`.
- **Validate:** run the new or changed tests with `--grep`, then `bun run typecheck` and `bun run lint`; a `@readonly` test also with `TEST_ENV=live`. A failure you can't explain from code is a reason to look at the app (browser or API), not to loosen the test.
